# QualFrame public research beta workplan

Checkpoint: 2026-09-07. This is a workplan, not a claim that proposed capabilities exist.

## Accepted direction

- Develop from the public MIT-licensed codebase as the single authoritative product baseline.
- Deliver a downloadable local application using each researcher's provider API keys.
- Serve research teams currently using AI for qualitative coding through manual processes.
- Support Excel codebook import first; other qualitative software exchange formats follow demand.
- Focus the first comparison release on inter-configuration agreement and within-configuration stability. These are not accuracy or validity claims.
- Preserve CFIR as a reference method while making grouping, hierarchy aggregation, and evidence/context policies generic.
- Aim for publishable evaluations and source-backed public performance reporting.
- Prepare a polished interface, landing page, promotional video, and tutorial demonstration for November.

The previous requirement for completed human-reference calibration before first-release use is superseded for this agreement/stability release. Human review remains central; human-reference calibration and validated configuration promotion remain later work. Update the canonical product documents together when implementing this scope change so the interface, run states, and exports agree.

## Confirmed delivery scope and execution requirements

- One operator controls a study at a time; teams collaborate initially through portable review/export packages. Concurrent editing, server accounts, and merge resolution are outside this release.
- Support Windows and macOS; clean installation testing is required on both.
- Tutorial: November 11, 2026. Demo freeze: October 28, 2026.
- Exact provider configurations and live evaluation spending are selected before execution; no budget is authorized by this plan.

## Milestone 1 — Generic coding workflow and usable imports

1. Import an Excel codebook through a sheet/header preview and column mapper. Support stable code IDs, labels, definitions, parent IDs, inclusion/exclusion guidance, examples, and optional ratings. Validate duplicates, missing fields, cycles, and inconsistent hierarchy before import; keep original files and versions.
2. Replace mandatory network concepts in the generic workflow with optional typed metadata such as site, group, profession, or time point. Permit no groups, one group, unequal groups, and missing values under a declared policy. Preserve AMN names in its reference template.
3. Make parent-code aggregation optional. Distinguish deterministic parent membership aggregation from model-generated parent summaries, which require separate prompts and evaluation.
4. Keep exact coded evidence separate from display context. Expose context units and width as settings; derive surrounding text deterministically from source offsets where possible. A broader coded span is a reviewed evidence edit, not merely extra display context.
5. Provide flat and hierarchical generic templates with full-codebook, top-level, and custom partitioning. Preserve the existing AMN pipeline as a versioned compatibility template.

Acceptance: synthetic studies with a flat codebook and a hierarchical codebook complete without AMN-specific labels or mandatory roll-up/context-generation stages. Excel imports require no YAML editing. Existing AMN fixtures retain expected behavior.

## Milestone 2 — Complete live coding and evidence review

1. Add provider/model/effort and budget configuration through the interface. Store keys outside study exports and explain that configured source content is sent to the chosen API provider even though application storage is local.
2. Extend browser execution to approved live providers with dated pricing, an absolute ceiling, existing interval approvals, progress, failure recovery, and safe resume. Capture attempts, timing, reported usage, and estimated costs without labeling them reconciled billing.
3. Implement direct text-selection evidence editing, code changes, clear review reasons, and complete review/export status. Resolve the legacy CFIR exact-evidence adapter separately from generic offset-bearing coding.
4. Run a small synthetic live API test through import, coding, review, and export on the authoritative version. Deliberately exercise failure/resume and budget pause. Test each supported provider rather than inferring portability from one adapter.
5. Package a methods/evidence export with sources by hash, codebook, prompts, model settings, run provenance, review history, and explicit limitations.

Acceptance: a researcher completes the entire workflow without editing code or configuration files. The release has a dated end-to-end live verification record, reviewed outputs, and a reproducible synthetic fallback.

## Milestone 3 — Agreement and stability evaluation

Design the comparison record during Milestone 1; build the runner after the core live path works.

1. Reuse the existing evaluation protocol, metrics specification, rubric schemas, and paper-section scaffold. Preserve CFIR network/synthesis measures as an optional method-specific extension. The current evaluation command scaffolding is not an operational benchmark.
2. Freeze comparison units, codebook version, source hashes, configuration, and matching policy before scoring. Separate a fixed-unit comparison of code assignment from a free-span comparison that includes segmentation.
3. Store multiple independent runs per exact model/effort configuration. Use three repeats initially for engineering screening, then choose the publication sample and repeat count based on precision and cost; three is not a publication sufficiency claim.
4. Report inter-model/configuration agreement and within-configuration stability separately. Initial measures: per-code positive agreement, label-set Jaccard, appropriately specified chance-corrected agreement, exact and overlap-based span comparisons, missing/extra coding, evidence validity, codebook violations, failures, latency, and cost.
5. Define empty-set, no-code, missing-output, rare-code, duplicate-unit, unequal-input, and undefined-statistic behavior. Missing or failed model outputs must not silently become negative codes or disappear from denominators. Existing simple positional agreement helpers need alignment and length checks before scientific use.
6. Display distributions, per-code results, sample sizes, and uncertainty. Account for clustering within transcripts and repeated runs; pairwise comparisons are not independent observations. Treat transcript-level construct presence as a coarse measure, not equivalent to passage-level agreement.
7. Link every disagreement to source evidence and code definitions. Keep machine outputs immutable and score human-corrected outputs separately.
8. Freeze a publishable protocol before the final benchmark: research questions, sampling, held-out material where tuning occurs, exclusions, analyses, failure handling, and claim boundaries. Add blinded human assessment and reference coding in a later validity study.

Acceptance: the same frozen inputs reproduce the deterministic report; hand-calculated cases and seeded errors verify metrics; all displayed scores trace to observations. Model agreement is never labeled accuracy. Stability is never labeled exact future reproducibility of a remote API.

## Milestone 4 — Framework library and open-source release

Create versioned framework packs with original source, edition, stable IDs, hierarchy, citations, redistribution terms, and a separate label for validation status in QualFrame. Begin with CFIR and the user-imported Excel path; add TDF, BCT, and ERIC once their source content and applicable redistribution permissions are verified.

Do not treat all four as interchangeable constructs. Framework packs must preserve their intended analytic purpose and coding guidance. Do not bundle private adapted research codebooks. A framework being available does not mean its QualFrame prompt has been validated.

Source checks on 2026-09-07:
- CFIR tools: https://cfirguide.org/cfir-tools-templates
- BCT training-site terms restrict reproduction/modification without consent: https://www.bct-taxonomy.com/terms . This is a source-specific restriction, not a determination covering every publication of the taxonomy.
- Original ERIC compilation and supplementary material: https://pmc.ncbi.nlm.nih.gov/articles/PMC4328074/

Provide straightforward installers/launchers, sample studies, troubleshooting, API setup guidance, contribution instructions, and versioned release notes. Test on clean machines and supported operating systems. Keep core development and ordinary tests independent of paid APIs.

Acceptance: an unfamiliar researcher installs, opens a sample, imports an Excel codebook, supplies a key, completes a small study, and locates the exported methods record without developer intervention.

## Milestone 5 — UI, landing page, and video

Extend the existing public UI throughout the milestones. Priorities: understandable study progress, codebook preview, fast evidence navigation, selection-based editing, comparison views, clear recovery actions, keyboard use, and accessible contrast. Test realistic transcript/assignment volumes, not just tiny demos.

Observe a small pilot group from the intended research teams. Record setup time, task completion, points of confusion, review time, and recovery success. Fix observed obstacles before visual finishing.

Landing page: purpose, supported methods, download, sample study, API/data-flow explanation, documentation, citation, contribution link, and limitations. Display performance only from a frozen report with dataset scope, configuration, sample size, date, uncertainty, and a link to methods. Label preliminary findings clearly; do not translate agreement into an accuracy headline.

Video: capture the actual verified interface for a 60–90-second captioned overview and a 5–8-minute walkthrough. Story: Excel codebook → coding → compare runs → inspect disagreement → edit evidence → export. Use Remotion for edit timing, captions, zooms, and transitions; use generated imagery only for supporting title/brand assets. Keep numerical claims tied to the evaluated build. Include a network-independent cached fallback for the live tutorial.

## Pace and dependency order

Work by acceptance gates rather than waiting for calendar dates. A focused first coding beta may precede the full evaluation study. Baseline and import/contracts come first; live execution/review follows; comparison infrastructure follows that stable path. UI design and evaluation protocol drafting can proceed alongside implementation. Installers, pilot feedback, and framework-source checks need not wait for a completed manuscript. Record final video footage after the relevant interface is stable.

November deliverable: downloadable usable beta, sample data, clear API setup, a traceable agreement/stability example if the benchmark is complete, documentation, landing page, and rehearsed video/demo. A completed peer-reviewed publication is a separate milestone whose timing is not controlled by software development.
